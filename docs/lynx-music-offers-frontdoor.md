# Lynx Pardelle music offers front door

The [exact hostname manifest](../config/lynx-music-offer-hosts.json) covers 47 distinct offers under `music.lynxpardelle.com`. Each host serves its own Zoolanding draft at `/`. The dedicated CloudFront distribution reuses the selected production Angular SSR and static release. The music and festival domains continue to use their current distribution and certificate. The offer model is inactive when `FRONTEND_PRODUCTION_LYNX_MUSIC_OFFERS_PHASE` is unset.

Extending the current music distribution would require replacing its viewer certificate with a certificate covering its two existing aliases and `*.music.lynxpardelle.com`. The dedicated model uses the offers-only certificate and scopes its invocation grants to its own distribution ARN. The shared SSR's existing `*.lynxpardelle.com` host rule covers the offer names.

From **Domains**, use **Create records in Route 53** to create its ACM validation CNAME in the authoritative public `lynxpardelle.com` zone. The `aliases` phase requires `ISSUED` for the wildcard at this exact level. Keep the validation record for renewal.

Query `https://api.zoolandingpage.com.mx/runtime-bundle?domain=<host>&path=%2F&lang=es`. Verify the exact `domain`, the authored `pageId`, and the absence of a not-found result for every entry.
3. Confirm zero current A, AAAA, or CNAME records for the 47 offer hosts, a unique authoritative public zone, and no alias conflicts. Record the current music and festival HTTP status, CDN alias set, and certificate coverage. Resolve the exact current SSR release and prove that the planned front door points to that release.
4. Promote through the owning source-only branch process. Use **Lynx Music Offers Production Front Door** on the exact current `main` commit. Its source review covers the hostname manifest, operator, and CDK inputs. The general production job integrates source. The offer workflow reuses the protected production identity and requires all exact roots to resolve before it can review or execute activation.

## Front-door rollout

1. Dispatch `action=deploy`, `execution=review`, and `phase=generated`. Set `expected_source_sha` to the current `main` commit and `release_id` to the deployed production SSR release. The workflow projects only six additions against the live stack and retains the exact change set and digest. Review that inventory, then dispatch `execution=execute` with the same phase, action, source and release, plus the successful `reviewed_run_id` and `expected_review_digest`. Wait for CloudFront `Deployed`. Request the generated CloudFront hostname and confirm it serves the first offer using the audit host.
2. Repeat the review and execute sequence for `phase=aliases`. The operator discovers the one issued wildcard certificate in ACM and binds it only during the protected operation. The reviewed change set must contain exactly two non-replacing modifications, the new distribution and its viewer-request function. Wait for `Deployed` and verify the deployed aliases match the manifest.
3. Test each new hostname through the attached distribution while its public DNS stays unchanged. Use a connection override that preserves TLS SNI and request Host. Verify trusted TLS, expected title and canonical, the intended offer at `/`, and a genuine 404 for an invented route. Check images, contact CTA, and layout on desktop and mobile.

```powershell
curl.exe --fail --show-error --connect-to "${OfferHost}:443:${CloudFrontHost}:443" "https://${OfferHost}/"
```

4. Create one atomic, reviewed DNS batch containing exactly an A and an AAAA alias for each of the 47 names. Target the new IPv6-enabled CloudFront distribution, use `CREATE` for all 94 records, and use `EvaluateTargetHealth=false`. Abort on an occupied name and review the conflict. Confirm Route 53 returns `INSYNC` and compare the 94 created records against the approved batch. Existing site, name-server, and mail records are outside this batch.
5. Verify each offer from public DNS without connection overrides. Check HTTP redirects to its HTTPS hostname, HTTPS succeeds with the correct canonical, the linked assets load, and the inquiry UI opens the intended contact destination. Repeat the music and festival health checks and compare the existing site DNS and alias sets to the baseline.

## Rollback

If content is wrong before DNS cutover, retain the last reviewed stage and correct the draft or front door through the owning workflow. After cutover, first remove exactly the 94 created records with one `DELETE` batch using the live record values and abort on drift. Wait for `INSYNC` and verify the offer DNS answers and the original sites. Dispatch `action=rollback` with `phase=aliases` to review and execute the transition back to the generated distribution. To remove the six resources afterward, dispatch `action=rollback` with `phase=generated` and its own reviewed change set. Keep the ACM validation CNAME for renewal.
