# Lynx Pardelle music offers front door

The [exact hostname manifest](../config/lynx-music-offer-hosts.json) covers 47 distinct offers under `music.lynxpardelle.com`. Each host serves its own Zoolanding draft at `/`. The dedicated CloudFront distribution reuses the selected production Angular SSR and static release. The music and festival domains continue to use their current distribution and certificate. The offer model is inactive when `FRONTEND_PRODUCTION_LYNX_MUSIC_OFFERS_PHASE` is unset.

Extending the current music distribution would require replacing its viewer certificate with a certificate covering its two existing aliases and `*.music.lynxpardelle.com`. The dedicated model uses the offers-only certificate and scopes its invocation grants to its own distribution ARN. The shared SSR's existing `*.lynxpardelle.com` host rule covers the offer names.

## Offline review

Run `node --test test/lynx-music-offers-frontdoor.test.js` from the infrastructure checkout. The fixture synthesizes the baseline and both offer phases with the same synthetic release. It compares every existing resource and output. The `generated` phase adds a distribution, a viewer-request function, three scoped SSR permissions including the Function URL permission generated by CDK, and a distribution-domain parameter. It uses the shared origin access control. The `aliases` phase changes only the new distribution and its viewer-request function. The test verifies the exact 47 aliases and the HTTPS viewer policy. DNS cutover has its own step.

## Activation prerequisites

1. Use ACM in `us-east-1` to locate `*.music.lynxpardelle.com`. From **Domains**, use **Create records in Route 53** to create its ACM validation CNAME in the authoritative public `lynxpardelle.com` zone. The `aliases` phase requires `ISSUED` for the wildcard at this exact level. Keep the validation record for renewal.
2. Confirm all 47 hostnames resolve to their own production Runtime Read draft, with the corresponding published root page and public image assets. Query `https://api.zoolandingpage.com.mx/runtime-bundle?domain=<host>&path=%2F&lang=es`. Verify the exact `domain`, the authored `pageId`, and the absence of a not-found result for every entry.
3. Confirm zero current A, AAAA, or CNAME records for the 47 offer hosts, a unique authoritative public zone, and no alias conflicts. Record the current music and festival HTTP status, CDN alias set, and certificate coverage. Resolve the exact current SSR release and prove that the planned front door points to that release.
4. Prepare and promote a protected activation workflow for this site through the owning branch process. Include the hostname manifest and CDK sources in the exact source review. Use the [Zooberiah front-door workflow](zooberiah-production-frontdoor.md) as the review and execution reference. The general production job integrates source, and the alias operations workflow audits aliases and cleans up specifically enumerated retired names.

## Front-door rollout

1. Set the phase to `generated` in the reviewed workflow input. Synthesize the selected release, project the six additions against the live stack, and retain the exact change set, source, release, phase, and reviewed digest. Require the baseline and the existing production resources to match. Execute the reviewed change set through the owning production identity. Wait for CloudFront `Deployed`. Request the generated CloudFront hostname and verify it serves the first offer using the configured audit host.
2. Set the phase to `aliases` and supply the exact issued wildcard certificate ARN to the workflow's private activation input. Recheck the certificate, source, release, actual generated resources, and absence of conflicting aliases. Require exactly two modifications to new resources, the distribution and its viewer-request function. Retain and execute the reviewed change set. Wait for `Deployed` and verify the deployed aliases match the manifest.
3. Test each new hostname through the attached distribution while its public DNS stays unchanged. Use a connection override that preserves TLS SNI and request Host. Verify trusted TLS, expected title and canonical, the intended offer at `/`, and a genuine 404 for an invented route. Check images, contact CTA, and layout on desktop and mobile.

```powershell
curl.exe --fail --show-error --connect-to "${OfferHost}:443:${CloudFrontHost}:443" "https://${OfferHost}/"
```

4. Create one atomic, reviewed DNS batch containing exactly an A and an AAAA alias for each of the 47 names. Target the new IPv6-enabled CloudFront distribution, use `CREATE` for all 94 records, and use `EvaluateTargetHealth=false`. Abort on an occupied name and review the conflict. Confirm Route 53 returns `INSYNC` and compare the 94 created records against the approved batch. Existing site, name-server, and mail records are outside this batch.
5. Verify each offer from public DNS without connection overrides. Check HTTP redirects to its HTTPS hostname, HTTPS succeeds with the correct canonical, the linked assets load, and the inquiry UI opens the intended contact destination. Repeat the music and festival health checks and compare the existing site DNS and alias sets to the baseline.

## Rollback

If content is wrong before DNS cutover, retain the last reviewed stage and correct the draft or front door through the owning workflow. After cutover, first remove exactly the 94 created records with one `DELETE` batch using the live record values and abort on drift. Wait for `INSYNC` and verify the offer DNS answers and the original sites. Then revert the new distribution to its reviewed generated phase or remove the six dedicated resources through a separately reviewed change set. Keep the ACM validation CNAME for certificate renewal. Existing distribution, SSR feature configuration, mail and registry changes belong to their respective owners.
